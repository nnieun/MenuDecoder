# 일본 메뉴판 이해 서비스 — 프론트엔드 전용 기획서

작성일: 2026-09-09 · Codex 구현 전달용

이 문서는 프론트엔드의 구현 요구사항이다. 완료된 코드나 테스트 결과가 아니다. 사용자와 합의한 기능을 기준으로 작성했으며, 경로·화면 구성·구현 기본값은 아래 규칙을 따른다. 실제 백엔드 OpenAPI 명세가 확정되면 계약 차이를 확인해 조정한다.

## 1. 목표와 범위

일본어 메뉴판 사진을 올리면 한국어 메뉴 설명, 자동으로 검색된 참고 사진, 설명의 근거를 보여주는 모바일 중심 웹 서비스를 만든다. 사용자는 현재 메뉴판에 관해 후속 질문을 할 수 있다.

하나의 Git 저장소에서 frontend/와 backend/ 폴더로 나눈다. 프론트는 frontend/에서 React·TypeScript·Vite를 기본안으로 사용하고 백엔드와 설치·실행·배포 설정을 분리한다. Git 브랜치와 PR은 저장소 전체에서 공유한다. 설치 버전은 구현 시 호환성을 확인하고 잠금 파일로 고정한다.

### 첫 버전 필수 기능

- 촬영 또는 이미지 업로드, 미리보기, 회전·메뉴판 영역 선택.
- 일본어 메뉴판 분석 시작과 진행 상황 표시.
- 메뉴별 일본어 원문, 한국어 이름, 원문 가격, 설명, 참고 사진 표시.
- 사진은 사용자 클릭 없이 자동 검색되고 준비된 항목부터 표시.
- 문서의 페이지·섹션 출처와 사진 원본 페이지 확인.
- 같은 세션에서 후속 질문·응답.
- 잘못 읽힌 메뉴명 수정과 재분석 상태 표시.
- 일부 실패, 사진 없음, 네트워크 오류, 세션 만료 처리.
- 현재 분석 삭제와 새로운 메뉴판 분석.

로그인, 과거 분석 목록, 즐겨찾기, 예약·결제, 개인화 추천은 첫 버전에 포함하지 않는다. 현재 세션의 대화는 유지한다.

## 2. 프론트와 백엔드의 책임

| 프론트엔드 | 백엔드 |
| --- | --- |
| 파일 선택·미리보기·입력 검증 안내 | 실제 파일 검증·사진 처리 |
| 메뉴·사진·출처·대화 렌더링 | OpenAI 호출·번역·문서 및 사진 검색 |
| API 요청·상태 표시·오류 복구 | LangChain·LangGraph·Chroma·메모리 |
| 사용자 수정·삭제 요청 | 처리 중복 방지·접근 검증·실제 삭제 |
| 요청 번호로 오류 문의 지원 | Langfuse 추적·평가 기록 |

프론트에서 AI API, Chroma, PostgreSQL, Langfuse를 직접 호출하지 않는다. API 비밀 키를 브라우저 환경 변수나 번들에 넣지 않는다. RAG 실험 설정이나 내부 추적 화면을 관광객용 화면에 추가하지 않는다.

## 3. 페이지 구조와 화면 설계

| 화면 | 경로 기본안 | 핵심 내용 | 주요 행동 |
| --- | --- | --- | --- |
| 시작 | / | 서비스 설명, 촬영·사진 선택 | 사진 선택 |
| 사진 확인 | /upload | 미리보기, 회전, 영역 선택, 파일 오류 | 분석 시작·다시 선택 |
| 분석·결과 | /analyses/:analysisId | 진행 상태, 메뉴 카드, 현재 대화 | 질문·원문 수정·출처 확인·삭제 |

메뉴 상세, 출처 보기, 원문 수정은 분석·결과 화면의 패널 또는 대화상자로 제공한다. 별도 로그인·관리자 페이지는 만들지 않는다. 업로드 화면에 선택한 사진이 없으면 시작 화면으로 안내한다. 분석 주소만 열고 유효한 세션이 없으면 이전 내용을 노출하지 않는다.

### 시작 화면

한 문장으로 목적을 설명하고 촬영·사진 선택 버튼을 우선 배치한다. 기본 대상은 일본어 메뉴판, 결과는 한국어이다. 기기에서 촬영을 제공하지 못하거나 권한이 거절되면 파일 선택으로 진행할 수 있게 한다.

### 사진 확인 화면

이미지 전체를 확인하고 회전·영역 선택 후 분석할 수 있다. 변경된 이미지가 실제 업로드되는지 확인한다. 파일 검증 실패는 입력 근처에 이유와 해결 방법을 보여준다. 읽지 못한 글자를 프론트에서 임의로 보정하지 않는다.

파일 기본안은 JPEG·PNG, 한 요청에 사진 1장, 최대 3 MiB이다. 3 MiB는 3×1,048,576=3,145,728바이트이다. 이 값은 설계 기본값이며 최종 Swagger 계약과 일치시킨다. 지원하지 않는 형식은 안내하고, 실제 변환 기능 없이 확장자만 바꾸지 않는다.

### 분석·결과 화면

상단에 현재 사진과 전체 상태, 본문에 메뉴 카드, 하단에 질문 입력창을 둔다. 모바일에서는 카드 한 열을 기본으로 하고, 넓은 화면에서는 메뉴 목록과 대화 영역을 나눌 수 있다. 고정 입력창이 메뉴·출처·키보드 조작을 가리지 않게 한다.

메뉴 카드에는 다음 순서로 정보를 표시한다.

1. 일본어 원문과 한국어 음식명.
2. 메뉴판에 적힌 가격 문자열. 통화·세금·옵션을 추정하지 않음.
3. 참고 사진 또는 사진 검색 상태.
4. 한국어 음식 설명과 확인 필요 안내.
5. 설명 출처, 사진 출처, 원문 수정 버튼.

설명이 준비되면 먼저 표시하고 사진은 도착하는 대로 채운다. 성공한 메뉴는 다른 항목 실패로 사라지지 않는다. 사용자에게 검색 버튼을 눌러야 사진이 나타나는 구조를 만들지 않는다.

### 사진 표시 규칙

사진에는 ‘참고 사진’ 표시와 원본 페이지 링크를 제공한다. 검색 사진을 해당 식당이 제공한 실제 음식 사진으로 단정하지 않는다. 이미지 주소가 깨지면 대체 문구를 표시하고 기존 설명·출처는 유지한다. 음식명이 확인되지 않은 상태에 임의의 비슷한 사진을 넣지 않는다.

사진 없음과 아직 검색 중을 구분한다. 사진 후보 선택은 서버가 하고 프론트는 반환된 결과를 표시한다. 사진 오류가 발생했다고 서버의 사진 검색을 자동 무한 반복하지 않는다.

### 출처 패널

문서 출처와 사진 출처를 별도 그룹으로 표시한다. 문서명, 섹션 경로, 원문 링크, PDF의 실제 페이지 정보를 제공한다. 웹 문서에는 없는 페이지 번호를 만들지 않는다. pdf_page_index가 0부터 시작한다면 화면용 물리 페이지는 index+1로 표시하고, 인쇄 페이지가 있으면 둘을 구분한다. 최종 OpenAPI에서 인덱스 기준을 확인한다.

인용 번호를 누르면 해당 근거로 이동한다. 출처 없는 주장에 임의 링크를 붙이지 않는다. 안전하게 허용된 URL만 링크로 열고 모델 출력의 HTML·스크립트를 실행하지 않는다.

### 대화 영역

질문과 응답, 처리 중 상태, 응답의 출처를 구분한다. 서버가 되묻는 경우 질문을 그대로 보여주고 응답을 기다린다. 프론트가 이전 메시지를 근거로 답을 만들어 내지 않는다. 보내는 중인 질문의 중복 전송을 막고 실패 메시지는 같은 요청을 재시도할 수 있게 한다.

다른 메뉴판으로 전환할 때 이전 대화를 새 분석에 붙이지 않는다. 현재 분석의 식별자와 세션 토큰이 일치해야 한다.

### 원문 수정·삭제

수정창에는 원문과 현재 항목 버전을 보여주고, 제출 중 중복 요청을 막는다. 성공하면 해당 항목을 재분석 상태로 표시한다. 오래된 응답이 도착해 수정 전 내용으로 돌아가지 않게 한다.

분석 삭제는 확인창으로 의도를 확인한다. 삭제 성공 후 토큰·대화·사진 미리보기를 정리하고 시작 화면으로 이동한다. 서버 삭제 실패 시 삭제 완료라고 표시하지 않는다. 화면 이탈·통신 취소만으로 서버 작업이 삭제됐다고 간주하지 않는다.

## 4. 상태와 사용자 안내

아래 명칭은 사용자용 표현이다. 실제 API 열거형과 매핑하는 파일을 따로 두고 OpenAPI 기준으로 관리한다.

| 상태 | 화면 안내 | 처리 |
| --- | --- | --- |
| 접수 | 메뉴판을 받았어요 | 자동 처리 시작 |
| 원문 분석 | 메뉴 이름을 읽고 있어요 | 진행 표시 |
| 원문 확인 필요 | 잘 읽히지 않는 부분을 확인해 주세요 | 수정·재촬영 제공 |
| 문서 검색 | 음식 설명을 찾고 있어요 | 기존 결과 유지 |
| 사진 검색 | 참고 사진을 찾고 있어요 | 카드별 로딩 |
| 일부 완료 | 준비된 메뉴부터 보여드려요 | 완료 항목 표시·나머지 진행 |
| 완료 | 분석이 완료됐어요 | 자동 계속 요청 종료 |
| 실패 | 분석을 완료하지 못했어요 | 원인·재시도 가능 여부 |
| 사용 제한 | 잠시 분석을 이용할 수 없어요 | 서버 안내에 따라 중단 |
| 세션 만료 | 이용 중인 세션이 만료됐어요 | 새 분석 안내 |

서버가 제공하지 않는 완료 퍼센트나 예상 시간을 임의로 표시하지 않는다. 전체 상태·개별 메뉴 상태·대화 처리 상태를 별도 관리한다.

## 5. FastAPI REST API와 Swagger 연동

백엔드의 /docs는 Swagger UI, /openapi.json은 계약의 기준 문서로 요구한다. 프론트는 백엔드가 제공한 명세 버전에서 TypeScript 타입을 생성하고, 수동으로 별도 계약을 늘리지 않는다. 아래 표는 기존 합의에 따른 구현 계약 초안이며 서버 구현 완료를 뜻하지 않는다.

| 요청 | 정상 응답 | 프론트 동작 |
| --- | --- | --- |
| GET /health | 200 | 연결 확인. 실제 분석 요청 아님 |
| POST /api/v1/analyses | 202 | multipart 사진 제출, analysis_id·세션 토큰 확보 |
| GET /api/v1/analyses/{id} | 200 | 진행·메뉴·대화 결과 반영 |
| POST /api/v1/analyses/{id}/continue | 200 | 실행 구간 진행 후 상태 반영 |
| POST /api/v1/analyses/{id}/messages | 202 | 후속 질문 접수 후 계속 실행 |
| PATCH /api/v1/analyses/{id}/items/{item_id} | 202 | 원문·기대 버전 제출 후 재처리 |
| DELETE /api/v1/analyses/{id} | 204 | 본문을 JSON으로 읽지 않고 삭제 완료 처리 |

202 응답은 접수이며 완료가 아니다. multipart 필드명, 세션 토큰 반환 위치, 상태 열거형, continue 본문은 OpenAPI로 확정한다. 불명확한 계약은 별도 이슈로 남기고, 프론트 편의를 위해 서버가 반환하지 않는 값을 실제 값처럼 사용하지 않는다.

### 자동 진행 규칙

분석 접수 후 프론트가 continue를 자동 호출하고 반환 상태를 반영한다. remaining_work가 있고 현재 상태가 실행 가능하면 다음 구간을 이어간다. 완료·실패·사용자 확인 대기·제한·삭제·세션 만료에서는 멈춘다. 같은 분석에 하나의 실행 요청만 진행하고 렌더링·재마운트 때문에 요청이 중복되지 않게 한다.

GET은 결과 조회이며 분석을 새로 실행시키지 않는다. 화면이 다시 활성화되면 먼저 최신 상태를 조회한 뒤 필요한 실행만 이어간다. 서버에서 잔여 작업이 있다고 해서 모든 상태에서 계속 호출하지 않는다. 백그라운드 탭에서는 자동 요청을 일시 정지하고 복귀 후 상태를 동기화하는 기본안이다.

Idempotency-Key는 같은 사용자 작업의 네트워크 재시도에 동일 값을 쓰고, 새로운 질문·새 실행 구간에는 새 값을 쓴다. 접수 최초 요청에는 아직 세션 토큰이 없으므로 서버의 최초 접수 중복 방지 계약을 확인한다. 응답 유실 때문에 사진을 새 키로 재접수하는 루프를 만들지 않는다.

### 화면에 필요한 데이터

| 묶음 | 주요 필드 |
| --- | --- |
| 분석 | analysis_id, status, state_version, items, messages, remaining_work, request_id |
| 메뉴 | item_id, original_name, translated_name, original_price_text, description, item_version, status, citations, images, warnings |
| 문서 출처 | source_id, document_title, source_url, section_path, pdf_page_index, printed_page_label, chunk_id |
| 사진 | image_id, image_url, source_page_url, caption, reference_only |
| 대화 | message_id, role, content, status, referenced_item_ids, citations |
| 오류 | error.code, error.message, error.retryable, error.details, request_id |

필수·선택·null 여부는 생성된 타입으로 확인한다. null, 빈 배열, 빈 문자열은 서로 구분해서 표시한다. 빈 가격은 0원으로 바꾸지 않는다.

### 오류 처리

| 코드·상황 | 동작 |
| --- | --- |
| 401 | 토큰 유효성 문제 안내, 자동 재요청 중단 |
| 404 | 접근할 수 없는 분석 안내. 다른 사람의 정보 유추 금지 |
| 409 | 최신 상태 조회, 수정 내용 보존, 재제출 안내 |
| 413·415·422 | 파일 크기·형식·입력 오류 안내 |
| 429 | 서버의 재시도 조건 확인, 사용 제한이면 자동 실행 중단 |
| 502·503·504 | 기존 결과 보존, 재시도 가능한 경우만 사용자에게 제공 |
| 연결 끊김 | 입력 유지, 연결 복귀 시 상태 조회부터 수행 |
| 이미지 로드 실패 | 사진 영역만 대체, 문서 설명은 유지 |

모든 오류를 ‘다시 시도’ 한 문구로 처리하지 않는다. 표시용 메시지는 한국어로 두고 내부 스택·비밀값을 노출하지 않는다.

## 6. 세션·보안·접근성

세션 토큰은 Authorization Bearer 헤더에 넣는다. 현재 탭의 sessionStorage에 저장하고 URL·로그·분석 도구에 남기지 않는다. 만료는 서버 판단을 따른다. 사용자 메뉴·대화를 브라우저 영구 저장소에 자동 보관하지 않는다.

환경 변수에는 백엔드 주소와 공개 가능한 설정만 둔다. 미리보기 객체 URL은 교체·삭제·화면 종료 시 해제한다. 외부 이미지·출처 주소의 허용 프로토콜을 확인하고, AI 응답에 원시 HTML 실행을 허용하지 않는다. 권한 검증은 백엔드 책임이며 프론트 제한만으로 보안을 보장한다고 설명하지 않는다.

버튼·입력에는 읽을 수 있는 이름을 제공한다. 대화상자는 키보드 이동·닫기·원래 위치로 초점 복귀가 가능하게 한다. 진행 상태·오류는 스크린리더에도 전달하고 색상만으로 구분하지 않는다. 모바일 가로 넘침, 화면 키보드에 가려지는 입력창, 긴 일본어·URL 줄바꿈을 확인한다.

## 7. 코드 구성과 개발 모드

src 아래 pages, features/upload, features/analysis, features/chat, features/citations, components, api, hooks, types, mocks 역할을 분리하는 기본안이다. HTTP 요청과 세션 처리는 api 계층에서 관리하고 화면마다 중복 구현하지 않는다. 서버 결과를 로컬 화면 상태와 구분한다.

백엔드가 준비되기 전에는 OpenAPI 초안에 맞춘 모의 응답으로 화면을 만든다. 모의 모드임을 표시하고 실제 연결 오류를 자동으로 모의 성공으로 바꾸지 않는다. 모의와 실제 모드는 같은 API 인터페이스를 사용한다.

필수 모의 시나리오는 정상, 일부 완료, 원문 확인 필요, 사진 없음, 빈 출처, 긴 대화, 세션 만료, 수정 충돌, 사용 제한, 삭제 실패이다. 모의 결과는 테스트용 예시임을 밝힌다.

## 8. 브랜치·커밋·PR

main은 실행 가능한 통합 상태로 유지하고 작업별 짧은 브랜치를 사용한다. 별도 develop 브랜치는 기본안에서 두지 않는다.

| 브랜치 | 예시 |
| --- | --- |
| feat/<작업명> | feat/menu-upload, feat/chat-panel |
| fix/<작업명> | fix/duplicate-request |
| refactor/<작업명> | refactor/api-client |
| docs/<작업명> | docs/frontend-setup |
| test/<작업명> | test/session-expiry |
| chore/<작업명> | chore/frontend-ci |
| experiment/<작업명> | experiment/card-layout |
| hotfix/<작업명> | hotfix/session-reset |

이름은 영문 소문자·숫자·하이픈을 사용한다. 커밋은 type(scope): 변경 내용으로 작성한다. 예: feat(ui): 메뉴 카드 추가, fix(api): 중복 분석 요청 차단. type은 feat, fix, refactor, docs, test, chore, perf를 기본으로 둔다.

한 PR에는 하나의 목적을 담고 변경 이유·화면 영향·API 버전·시험 방법·미해결 사항을 작성한다. 혼자 개발하므로 타인의 승인을 필수 게이트로 두지 않는다. 검사 후 squash merge하고 작업 브랜치를 정리한다. 백엔드 변경이 필요하면 같은 목적의 PR에 frontend/와 backend/ 변경을 함께 담고 명세 버전을 맞춘다. 별도 PR로 나누는 경우 의존 관계를 기록한다.

## 9. 구현 순서와 완료 기준

1. 독립 프로젝트, 환경 변수, 라우팅, API 계층·타입과 모의 모드.
2. 시작·사진 확인·분석·메뉴·출처 화면.
3. 자동 continue·부분 결과·세션·오류·수정·삭제.
4. 후속 대화, 실제 백엔드 연동, API 계약 차이 해결.
5. 핵심 흐름 시험, 모바일·키보드 점검, 독립 배포와 안내 문서.

‘첫 기능 완료’는 촬영 → 분석 → 설명·자동 사진·출처 → 후속 질문이 실제 백엔드와 이어지고, 실패·삭제·세션 분리가 동작하는 상태이다. 모의 모드 완성과 실제 연동 완료는 별도 기록한다.

CI는 잠금 파일 기준 설치, 코드·타입 검사, 핵심 시험, 빌드를 수행한다. 명세 변경 시 생성 타입의 갱신 여부를 확인한다. 실제 AI 호출을 매 PR 기본 시험으로 반복하지 않는다. 프론트는 Vercel 독립 배포를 목표로 하고 라우트 직접 접근·새로고침·API 주소·CORS 연동을 확인한다. 배포 성공이나 무료 조건을 시험 전에 확정적으로 보고하지 않는다.

## 10. Codex 전달 규칙

이 파일을 프론트 구현의 기준으로 사용하고, 전체 산출물 책임은 별도 project_deliverables.md를 참고한다. 백엔드의 RAG·임베딩·OCR 코드를 frontend/ 폴더에 구현하지 않는다. 서버 Swagger/OpenAPI를 받으면 계약을 확인하고 없으면 모의 화면 개발을 먼저 수행한다.

완료 보고에는 변경 파일, 실행·시험 결과, 실제 연동 여부, 미완료 항목과 이유를 포함한다. 실제 실행하지 않은 결과·URL·성능값을 만들지 않는다. 백엔드가 없는 상태를 프론트의 가짜 AI 결과로 감추지 않는다.


## 단일 저장소의 공통 Git 작성자 규칙

아래 규칙을 구현 저장소 루트 AGENTS.md에 한 번 작성하여 frontend/와 backend/에 공통 적용한다. 하위 폴더의 안내 문서에는 필요할 때 해당 파일을 참조한다. 현재는 기획서에 요구사항을 반영한 것이며 실제 저장소의 AGENTS.md를 생성한 것은 아니다.

- 커밋 author와 committer는 사용자가 지정한 이름·이메일을 사용한다.
- GPT·Codex·Claude 및 기타 AI·봇 명의로 커밋하지 않고 AI·봇 공동 작성자 표기를 추가하지 않는다.
- 커밋 전에 실제 적용되는 작성자 정보를 확인한다. 정보가 없거나 사용자 지정 정보와 다르면 커밋을 중단하고 확인한다.
- 사용자 승인 없이 Git 작성자 설정을 바꾸거나 환경 변수로 덮어쓰지 않는다.
- push는 사용자가 승인한 GitHub 계정으로만 수행한다.

CI는 변경 경로에 따라 프론트·백엔드 검사를 선택하고, 공통 계약·루트 설정이 변경되면 관련 검사를 모두 실행한다. 폴더 분리는 Git 저장소나 작성자 계정을 분리한다는 뜻이 아니다.
