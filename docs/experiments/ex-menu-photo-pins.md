# 메뉴판 사진 위 번호 핀 — 위치 추정 정확도 실험과 채택

날짜: 2026-09-13 · 상태: 채택(번호 핀 방식), "원문 자리에 한국어 덮어쓰기"는 기각

## 문제

메뉴판 사진을 보면서 어떤 한글 번역이 사진의 어느 메뉴에 대응하는지 알기
쉽게 하고 싶었다. 사용자가 제시한 이상적인 모습은 Google Lens처럼
원문 자리에 직접 한국어를 덮어쓰는 것.

## 시도 1: PaddleOCR 줄 단위 인식 + 텍스트 유사도 매칭

`backend/rag/fixtures/images.jpg`(실제 이자카야 메뉴판, 13개 항목)로
PaddleOCR 텍스트 검출 결과(줄 단위, polygon 포함)를 OpenAI가 추출한
정확한 메뉴 이름과 `difflib.SequenceMatcher`로 매칭했다.

**결과: 13개 중 3~4개가 완전히 다른 항목의 위치에 잘못 매칭됨.**
원인은 실제 사진에서 한 줄에 메뉴 두 개가 붙어 인식되는 경우
(`'まぐろ井¥(.130(1.243)沈子¥半1.780'`처럼 두 항목이 한 블록)가 많아서,
穴子丼을 찾으려는 매칭이 엉뚱하게 うな丼 블록에 걸리는 식의 실패가
재현됐다. **기각.**

## 시도 2: OpenCV 형태학적 연산으로 단어 단위 재분할

줄 단위 병합 문제를 피하려고 OpenCV(Otsu 이진화 + 모폴로지 닫기 연산)로
직접 단어 단위 연결요소를 찾고, 각 크롭을 PaddleOCR의 `TextRecognition`
(검출 없이 인식만)에 넣어봤다.

**결과: 13개 중 0개 매칭.** 사진이 비닐 파일에 넣어 촬영된 것이라
반사·테두리·빨간 끈까지 전부 전경으로 잡혀 페이지 전체가 하나의
연결요소로 뭉쳐버렸다. 전처리(반사 제거, 기울기 보정)를 별도로
해결해야 하는 문제라 **기각.**

## 시도 3: 비전 모델에게 직접 대략적 위치를 요청 — 채택

OCR로 위치를 역추적하는 대신, 메뉴를 추출하는 바로 그 OpenAI 비전
호출에서 `center_x`, `center_y`(0~1 비율, 대략적 위치)를 함께
요청했다. 추가 API 호출 없이 같은 호출에 필드만 추가한 것이라 비용
증가가 없다.

같은 사진으로 2회 반복 실행:

| 실행 | 정확 | 한 줄 정도 어긋남 | 완전히 다른 위치 |
| --- | --- | --- | --- |
| 1차 | 7/13 | 3/13 (6~8번, 회 모둠 섹션) | 3/13 (9~11번) |
| 2차 | 10/13 | 3/13 (9~11번, 참치·칸파치·문어회) | 0/13 |

두 실행 모두 **이름이 다른 항목과 뒤바뀌는 사고는 없었다** — 번호와
이름의 대응은 항상 정확했고, 오차는 항상 "위치가 한 줄 정도 밀림" 수준
(참치회·칸파치회·섬문어회처럼 줄 간격이 좁은 구간에서 반복적으로 발생)
이었다. 완전 정밀한 텍스트 덮어쓰기에는 부족하지만, "대략 이 근처"를
가리키는 용도로는 실사용 가능하다고 판단해 **채택**했다.

## 실제 구현

- `backend/models.py`: `MenuItem.center_x`/`center_y` (0~1, nullable) 추가
- `backend/provider.py`: `EXTRACT_LOCATION_HINT`를 비전 추출 프롬프트에만
  추가(`backend/ocr.py`의 OCR-텍스트 전용 구조화 경로는 이미지가 없으므로
  제외 — 위치를 지어내지 않도록)
- `backend/mock.py`: 모의 모드에서도 프론트 테스트가 가능하도록 고정된
  좌표 부여
- 프론트(`AnalysisPage.tsx`): 원본 사진 위에 번호 핀 표시, 탭하면 이름·
  가격 말풍선. 메뉴 카드에도 같은 번호 배지를 달아, 핀 위치가 어긋나도
  번호로 카드를 찾을 수 있게 함. "번호는 대략적인 위치이며 한 줄 정도
  어긋날 수 있다"고 화면에 명시해 실제 정확도 이상으로 신뢰하지 않도록 함

## 한계

- 실제 사진 1장(이자카야 메뉴판, 붓글씨체)에 대한 2회 반복 실행일 뿐이다.
  다른 폰트·레이아웃(활자체 메뉴판 등)에서는 정확도가 다를 수 있다.
- 줄 간격이 좁은 구간에서 체계적으로 오차가 발생하는 패턴이 두 실행
  모두에서 관찰됐지만, 프롬프트 개선으로 고칠 수 있는지는 시도하지 않았다.
- "정확한 위치"가 아니라 "대략적 위치"로 사용자 기대치를 명시적으로
  낮췄기 때문에 채택했다 — 같은 정확도로 "정밀한 텍스트 대체" UX를
  약속했다면 채택하지 않았을 것이다.
